# 第3章　なぜコンテキストエンジニアリングなのか

- ページ作成日時：2026-08-01 14:54 JST
- 最終更新日時：2026-08-01 14:54 JST

対象論文：Lingrui Mei et al., *A Survey of Context Engineering for Large Language Models*, arXiv:2507.13334v2, 2025.

## 要点

第3章は、本論文の核心である。著者らは、従来のプロンプトエンジニアリングが単一の静的文字列を調整する問題として理解されてきたのに対し、現代のLLMシステムでは、指示、外部知識、ツール定義、メモリ、状態、ユーザー要求を動的に組み立てる必要があると論じる。

この転換を、論文は次の式で表す。

```text
C = A(c1, c2, ..., cn)
```

ここで `C` はモデルへ渡される最終コンテキスト、`ci` は個々のコンテキスト構成要素、`A` はそれらを選択・整形・連結する組立関数である。

この定式化の価値は、プロンプト文面の工夫を、検索、選択、圧縮、メモリ、ツール、状態管理を含むシステム最適化問題へ拡張した点にある。一方で、論文が示す数理表現は厳密な理論というより、研究領域を整理するための概念モデルとして読むべきである。

## 本章の概要

著者らは、現代のLLMアプリケーションが単一の静的プロンプトを処理するものではなく、動的で構造化された多面的な情報ストリームを利用すると説明する。この変化を扱うため、コンテキストエンジニアリングを独立した領域として定義する。

第3.1節では、自己回帰型LLMの条件付き生成を出発点に、コンテキストを複数の構成要素から組み立てられるものとして形式化する。第3.2節では、計算量、信頼性、プロンプト最適化の属人性、性能向上、資源効率、将来の適応能力という観点から、なぜコンテキストエンジニアリングが必要なのかを論じる。

## 重要な引用

### 引用1：プロンプト中心の理解からの離脱

論文は、現代のLLMシステムが単一の静的文字列を処理するのではなく、動的で構造化された多面的な情報ストリームを利用すると述べる。

#### コメント

重要なのは「プロンプトが不要になった」という意味ではない。プロンプトは依然として重要だが、最終コンテキストを形成する一要素へ位置づけ直される。プロンプトエンジニアリングからコンテキストエンジニアリングへの転換は、置換ではなく包含関係の再定義である。

### 引用2：情報ロジスティクスへの転換

著者らは、この変化をプロンプト設計の「技芸」から、情報ロジスティクスとシステム最適化の「科学」への転換として表現する。

#### コメント

この表現は本論文の野心をよく示す。ただし、検索・圧縮・組立を形式化しただけで自動的に科学になるわけではない。再現可能な評価方法、失敗原因の切り分け、コスト・安全性・来歴を含む設計変数が必要になる。

## 内容整理

### 1. 自己回帰生成とコンテキスト

論文は、モデル `θ` がコンテキスト `C` を条件として出力列 `Y` を生成する標準的な自己回帰モデルから議論を始める。

```text
Pθ(Y | C) = Π Pθ(yt | y<t, C)
```

この式自体は新しくない。重要なのは、条件 `C` を何とみなすかである。

従来のプロンプトエンジニアリングでは、暗黙に次のような理解が採られていた。

```text
C = prompt
```

本論文は、この見方では現代のLLMシステムを記述できないとする。

### 2. コンテキストを構成要素へ分解する

著者らは、最終コンテキストを組立関数によって構成されるものとして表す。

```text
C = A(c1, c2, ..., cn)
```

論文が挙げる主要な構成要素は次のとおりである。

- `cinstr`：システム指示と規則
- `cknow`：RAGや知識グラフなどから取得した外部知識
- `ctools`：利用可能なツールの定義とシグネチャ
- `cmem`：過去の相互作用から保持されたメモリ
- `cstate`：ユーザー、環境、マルチエージェントシステムの動的状態
- `cquery`：ユーザーの現在の要求

この分解により、最終入力を一つの文章としてだけでなく、異なる由来・責任・更新頻度を持つ情報要素の合成として検討できる。

### 3. コンテキストエンジニアリングを最適化問題として捉える

論文は、組立、検索、選択などの関数集合 `F` を最適化し、タスク集合に対する期待出力品質を最大化する問題としてコンテキストエンジニアリングを表す。

```text
F* = arg max_F E[Reward(output, ideal output)]
```

制約として最も明示的なのは、コンテキスト長の上限である。

```text
|C| <= Lmax
```

この定式化によって、設計対象は単一のプロンプト文字列から、情報取得・選択・整形・配置を担うシステム関数へ移る。

### 4. 情報理論・ベイズ推論による説明

論文はさらに、検索された知識が正解に対して持つ相互情報量を最大化する問題、最適なコンテキストの事後分布を推定するベイズ的問題として説明する。

これらは、単なる意味類似度検索ではなく、現在の問題を解くためにどれだけ有益な情報かを選ぶべきだという方向を示している。

ただし、実際のシステムで理想出力や相互情報量を直接計算できるとは限らない。現状では理論的な設計目標を示す表現として理解するのが妥当である。

## プロンプトエンジニアリングとの比較

論文の比較表は、両者を次のように対比する。

| 観点 | プロンプトエンジニアリング | コンテキストエンジニアリング |
|---|---|---|
| モデル | 静的なプロンプト文字列 | 複数要素の動的・構造的組立 |
| 最適化対象 | 文字列 | 組立・検索・選択などの関数群 |
| 状態 | 主としてステートレス | メモリと動的状態を明示的に含む |
| 拡張性 | 長さと複雑性に対して壊れやすい | モジュール構成で複雑性を管理する |
| 障害解析 | 手作業による試行錯誤 | 個々のコンテキスト関数を評価・デバッグする |

この対比は理解しやすい一方、やや理想化されている。高度なプロンプトエンジニアリングにも自動最適化や動的生成は存在し、コンテキストエンジニアリングも実務では手作業と経験則に大きく依存している。

## 技術解説

### 組立関数は一つの関数とは限らない

式では `A` という単一の組立関数で表されるが、実システムでは複数段階のパイプラインになる。

```text
情報源の発見
→ 取得
→ 権限確認
→ 関連性評価
→ 重複除去
→ 圧縮・構造化
→ 優先順位付け
→ 配置
→ モデル入力化
```

したがって、`A` は単純な連結処理ではなく、複数の判断と変換を含む上位概念である。

### コンテキストの品質は情報量だけでは決まらない

論文は主に出力品質とコンテキスト長を最適化対象としている。しかし実運用では、少なくとも次の変数も必要になる。

- 正確性
- 鮮度
- 来歴
- 権限
- 機密性
- 取得・推論コスト
- 応答遅延
- 再現可能性
- 監査可能性

関連情報であっても、権限のない情報、期限切れの情報、出所不明の情報を入れてはならない。コンテキスト最適化は、多目的制約付き最適化として扱う必要がある。

### ロングコンテキストには二つの拡張がある

論文はコンテキストのスケーリングを二つに分ける。

1. **長さのスケーリング**：数千から数百万トークンへコンテキストウィンドウを拡張する。
2. **マルチモーダル・構造的スケーリング**：テキストだけでなく、画像、音声、動画、時系列、空間関係、参加者状態、意図、文化的背景などを扱う。

この区別は重要である。コンテキストエンジニアリングの問題は、単なるトークン長の問題ではなく、異質な情報を一貫した形で統合する問題でもある。

## 第3.2節：なぜ必要なのか

著者らは必要性を四つの観点から説明する。

### 現在の限界

- 自己注意機構の計算量とメモリ使用量
- 長い入力による遅延と料金
- ハルシネーションと入力不忠実性
- 入力表現の小さな差への過敏性
- プロンプト設計の主観性と属人性

### 性能向上

RAG、構造化プロンプト、思考過程の誘導、少数例示、ドメイン固有コンテキストなどが、特定タスクの性能を改善すると整理される。

### 資源最適化

必要情報の選択、圧縮、注意制御により、入力全体を無差別に処理するより少ない計算資源で性能を維持する方向が示される。

### 将来性

再学習を行わず、新しい課題や領域へ推論時に適応する仕組みとして、コンテキストエンジニアリングが位置づけられる。

## 私たちの考察

### 数式は理論の完成ではなく、設計対象の宣言である

第3章の数式は、コンテキストエンジニアリングの厳密な理論を完成させたものではない。現実には理想出力、報酬、情報価値、コンテキストの事後分布を正確に知ることは難しい。

それでも意味はある。最適化対象がプロンプト文字列ではなく、検索・選択・組立を担う関数群であることを明示したからである。

### 構成要素の列挙には不足がある

`cinstr`、`cknow`、`ctools`、`cmem`、`cstate`、`cquery` は有用な初期分類だが、実運用では次も独立して扱う価値がある。

- 情報の来歴と信頼度
- 権限と公開範囲
- 時刻・期限・鮮度
- 現在の作業計画と未完了事項
- 生成物の検証結果
- 失敗履歴と復旧状態

これらを単なるメタデータとして後付けするか、主要構成要素として扱うかは、今後の設計上の重要論点になる。

### 動的であることと自律的であることは同じではない

コンテキストが動的に組み立てられるからといって、モデル自身がすべてを決める必要はない。固定ルール、検索器、権限管理、人間の判断、別エージェントなどが組立へ関与できる。

自律性を高めるほど柔軟性は増すが、再現性、説明責任、安全性は低下し得る。どの判断をどの主体へ委ねるかも、コンテキストエンジニアリングの設計対象である。
