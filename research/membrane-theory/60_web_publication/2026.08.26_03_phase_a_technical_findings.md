# 公開版「膜」Phase A 技術確認結果

- ページ作成日時：2026-08-26 13:06 JST
- 最終更新日時：2026-08-26 13:06 JST
- status：technical findings / publication platform request required

## 結論

`/membrane/` および `/membrane/.../` のnested route自体は、現行 `new_document_publication.py` と `build_structured_preview.py` のroute規則で扱える。

一方、`scripts/build_site_manifest.py` は `/membrane/` namespace を `content/membrane/` のMarkdown正本へ対応付ける規則を持っていない。

このまま公開すると、`site/membrane/.../index.html` はroute manifestには現れるが、`corresponding_content_path` が `null` となり、`content_source_status` が `html_only`、page typeも既定では `utility` となる。

公開版「膜」で採用する `source archive -> public edition Markdown -> site HTML` の契約と合わないため、publication基盤担当へ最小修正を依頼する。

この担当チャットでは基盤コードは変更しない。

## 確認したこと

### 1. nested source path

registryの`source`は、`content/`配下のMarkdownであれば階層制限がない。

したがって、次は許容される。

```text
content/membrane/index.md
content/membrane/about.md
content/membrane/research-map.md
content/membrane/thoughts/exchange-device.md
content/membrane/reading/<slug>.md
```

### 2. nested route

route validatorは絶対directory routeを許容しており、次は形式上通る。

```text
/membrane/
/membrane/about/
/membrane/research-map/
/membrane/thoughts/exchange-device/
/membrane/reading/<slug>/
```

candidate builderもslugから階層をそのまま生成するため、nested route自体の追加対応は不要。

### 3. canonical

production sourceでは、front matterの`canonical_url`がregistry routeと完全一致することを要求する。

例：

```text
slug: /membrane/
canonical_url: https://genai-ron.jp/membrane/
```

この契約はそのまま利用できる。

### 4. 最初の `/membrane/` のindex契約

production文書は、公開前に`index_source`と`index_html`の双方へ対象routeのリンクがちょうど1件必要。

最初の`/membrane/`では、既存のGENAI-RONトップをindexとして使える。

候補：

```text
index_source: content/index.md
index_html: site/index.html
```

両方に`/membrane/`への導線を1件置いたうえでprepareする。

`/membrane/about/`以降は、公開済みの膜トップをindexとして使う設計が可能。

### 5. theme

現行structured previewでは非series文書に通常のsite headerが使われる。`default-academic`はproduction-enabledであり、最初の技術通しには利用可能。

膜専用themeはPhase Aの必須条件ではない。

### 6. manifest上の問題

`build_site_manifest.py` の `content_path_for()` は、現状、home / article / essay / notes / seriesのみを明示的に対応付ける。

`/membrane/` は該当しないため、公開HTMLが存在しても `content/membrane/...` の正本を発見できない。

`page_type_for()`にもmembrane固有の分類がないため、既定の`utility`になる。

## publication基盤担当への修正依頼範囲

最小修正でよい。

1. `build_site_manifest.py::content_path_for()` に `/membrane/` namespaceを追加する。
2. routeとMarkdownの対応を以下にする。

```text
/membrane/                           -> content/membrane/index.md
/membrane/about/                     -> content/membrane/about.md
/membrane/research-map/              -> content/membrane/research-map.md
/membrane/thoughts/<slug>/           -> content/membrane/thoughts/<slug>.md
/membrane/reading/<slug>/            -> content/membrane/reading/<slug>.md
/membrane/bibliography/              -> content/membrane/bibliography.md
```

3. `page_type_for()` も最低限、膜トップと内部文書を`utility`以外で識別できるようにする。命名は既存分類方針に合わせて基盤担当側で決めてよい。
4. 既存route / article / notes / seriesの挙動を変えない。
5. manifest build / `--check` と既存publication laneのtestを通す。
