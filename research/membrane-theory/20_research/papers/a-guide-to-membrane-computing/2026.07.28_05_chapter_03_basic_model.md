# 『A Guide to Membrane Computing』第3章｜The basic model

## 原著情報

- Gheorghe Păun, Grzegorz Rozenberg
- “A Guide to Membrane Computing”
- *Theoretical Computer Science*, 287 (2002), pp. 73–100
- 対象箇所：Section 3, “The basic model”

## この章の位置づけ

第1章と第2章では、生物膜からどの特徴を抽象化するかが説明された。第3章では、その抽象化が初めて数学的な計算モデルとして定義される。

ここで重要なのは、P systemが単に「複数の箱の中で処理を行うモデル」ではないことである。膜構造、局所的なオブジェクト集合、進化規則、優先関係、通信先、膜の消滅、同期的な並列実行が、一つの構成として結び付けられる。

## 1. 膜構造の表現

膜構造は、入れ子になった膜の階層である。原著では、次の三つの表現が対応するとされる。

- Euler–Venn図
- 木構造
- 対応する括弧列

例えば、膜の包含関係は、ラベル付き括弧によって次のように表現できる。

```text
[1 [2]2 [3]3 [4 [5]5 [6 [8]8 [9]9]6 [7]7]4]1
```

同じ親膜の内側に並ぶ隣接膜の順番には意味がない。したがって、括弧列は一意ではないが、包含関係としての木は同じである。

### SGOSとの接点

SGOSにおけるProject、Area、Agent、Repository、Human-facing layerを膜として考える場合、重要なのは表示順ではなく包含・隣接・透過可能性である。

フォルダツリーと膜構造は似ているが同一ではない。フォルダは原則として静的な所属を表すのに対し、膜モデルでは、各領域が固有の状態と規則を持ち、通信と変形に参加する。

## 2. 多重集合としてのオブジェクト

各領域にはオブジェクトの多重集合が置かれる。同じ種類のオブジェクトが何個存在するかが重要であり、並び順には意味がない。

形式上は文字列によって多重集合を表すが、文字の順番ではなく各記号の出現回数だけを見る。これはParikh写像によって表現される。

例えば、文字列 `aabbc` は、次の個数ベクトルに対応する。

```text
(a: 2, b: 2, c: 1)
```

### SGOSとの接点

P systemのオブジェクトを、SGOSの文書やメッセージとそのまま同一視することはできない。P systemでは、オブジェクトは意味内容よりも、種類・個数・所在によって扱われる。

一方で、次のような状態トークンには近い。

- 未処理Requestが3件ある
- 承認待ちEnvelopeが2件ある
- 特定のCapability tokenが1個存在する
- あるContext fragmentが対象領域に投入された

したがって、SGOSを膜モデルとして記述する場合、自然言語そのものより、自然言語から抽出された状態・権限・要求・成果物参照をオブジェクトとして扱う方が近い。

## 3. P systemの形式定義

この章で扱うP systemは、概略として次の構成を持つ。

```text
Π = (V, T, C, μ, w1, ..., wm, (R1, ρ1), ..., (Rm, ρm))
```

各要素の意味は次の通りである。

- `V`：オブジェクトのアルファベット
- `T`：出力として数えるオブジェクトの集合
- `C`：触媒となるオブジェクトの集合
- `μ`：ラベル付き膜構造
- `wi`：各領域の初期多重集合
- `Ri`：各領域に属する進化規則
- `ρi`：各領域の規則間の優先関係
- `m`：膜の数。P systemのdegree

この定義から、P systemの計算能力は中央の一個の制御装置に置かれていないことが分かる。構造、局所状態、局所規則、通信指定が分散して計算系を作る。

## 4. 進化規則

進化規則は一般に次の形を取る。

```text
u → v
```

左辺 `u` に含まれるオブジェクトが消費され、右辺 `v` に従って新しいオブジェクトが生成される。

右辺のオブジェクトには、移動先を示す指定を付けられる。

- `here`：現在の領域に残る
- `out`：外側の領域へ出る
- `inj`：直接内包される膜 `j` の領域へ入る

さらに `!` が付いた規則は、規則を実行した領域を囲む膜を溶解する。

### 消費されるということ

規則適用時、左辺に対応するオブジェクトは参照されるだけではなく、現在の多重集合から取り除かれる。これはデータベースの読み取りより、資源・状態・権限の遷移に近い。

SGOSに当てはめるなら、Requestを何度でも複製して読むモデルではなく、状態が `pending` から `accepted`、`completed` へ移り、以前の状態トークンが消費されるようなモデルに近い。

## 5. 協調規則と非協調規則

左辺に複数のオブジェクトを必要とする規則を持つ場合、そのシステムはcooperative systemと呼ばれる。一個のオブジェクトだけで発火できる規則しか持たない場合はnoncooperative systemである。

協調規則は、複数条件がそろったときだけ処理を進める。

```text
approval + request → executable_job
```

これはSGOSの承認制御と自然に対応する。ただし、この対応はあくまで構造上の類似であり、原著が人間の承認や組織運用を論じているわけではない。

## 6. 触媒

触媒は、他のオブジェクトの変化を助けるが、自身は規則適用後も残るオブジェクトである。

典型的には次の形で使われる。

```text
c a → c v
```

`c` は残り、`a` が `v` に変化する。

### SGOSとの接点

SGOSにおける触媒候補としては、次のようなものが考えられる。

- Charter
- Policy
- Schema
- Agent capability
- Human approval authority
- Repository Context

ただし、Repository Contextは単純な触媒より複雑である。文脈は処理を可能にするだけでなく、解釈や出力そのものによって変化し得るため、完全に不変な触媒ではない。

## 7. 優先関係

各領域では、規則同士に部分順序としての優先関係を設定できる。高い優先度の規則が適用可能である間、低い規則は選ばれない。

重要なのは、原著では「同じオブジェクトをどちらの規則が取るか」という局所的な奪い合いだけでなく、より高い規則が一つでも適用可能なら、低い規則への割当を抑える点である。

### SGOSとの接点

これは、単純なtask priorityより、governance gateに近い。

```text
停止条件 > 承認待ち > 通常実行
```

例えば、秘密情報混入の疑いがある場合、通常の公開処理を走らせない。これは高優先度の停止規則が、低優先度の作業規則を抑止する構造と見なせる。

## 8. 膜の溶解

規則の右辺に `!` が含まれると、その領域を囲む膜が消滅する。

その結果、次のことが起きる。

- 内部オブジェクトは外側の領域へ移る
- その領域に属していた進化規則は失われる
- 外側の膜も同時に溶解していれば、さらに上位へ移る
- 最外層のskin membraneは溶解しない

ここでは、膜は単なるアクセス境界ではなく、局所規則を保持する実行環境でもある。膜がなくなると、内部の内容だけが上位に残り、その領域固有の規則は消える。

### SGOSとの接点

これはAgent停止やProject終了に似ているが、重要な違いがある。

- 成果物や状態は上位領域へ返る
- その領域固有の処理能力・責務・規則は消える

したがって、SGOSのReturn HandoffやArea closeoutは、膜溶解の穏当な運用版として比較できる。

## 9. 構成、遷移、計算、停止

初期状態は、膜構造と各領域の初期多重集合によって定められる。

```text
(μ, w1, ..., wm)
```

規則の並列適用により、ある構成から次の構成へ遷移する。

```text
C1 ⇒ C2
```

この遷移列が計算である。

計算は、すべての領域で適用可能な規則がなくなったとき停止する。停止に到達した計算だけが成功した計算として出力を持つ。

### 停止の意味

停止は「処理時間が来たから終わる」ことではない。現在の状態から適用可能な変化が存在しなくなったことである。

SGOSにおいても、完了条件を時間や人間の宣言だけに依存させず、未処理Envelope、未解決Decision Request、適用可能なJob ruleが残っていない状態として記述できる可能性がある。

ただし、現実の組織や人間との協働では、外部入力を待っている休止状態と、本当の完了状態を分けなければならない。P systemの単純なhaltingをそのまま適用すると、waitingとcompletedを混同する。

## 10. 最大並列性と非決定性

各計算ステップでは、規則は非決定的かつ最大並列に適用される。

- どの規則とオブジェクトを選ぶかは一意に決まらない
- ただし選択後、さらに適用可能な規則を残さないところまで割り当てる
- 各領域は同期して一つのmacro-stepを進める

これは「可能な処理を全部同時に行う」だけではない。どの可能性を採るかには分岐があるが、採った分岐の中では資源を余らせず最大限に反応させる。

### SGOSとの非対応

現在のSGOSでは、すべてを最大並列に実行することは望ましくない。

- 外部書込みには承認が必要
- 同じ資源に対する競合を避ける必要がある
- 人間の注意資源は有限
- Context Economyのため、あえて動かさない方がよい

したがって、SGOSがP systemから借りるべきなのは最大並列性そのものではなく、局所反応の同時性、資源競合、分岐、同期境界の明示である。

## 11. 例題が示すもの

原著の例では三重の膜構造を用い、最内層でオブジェクトを増殖させた後、膜を溶解して中間領域へ内容を移す。中間領域では優先規則によって反応回数を制御し、最後にその膜も溶解する。最外層では生成された出力オブジェクトを環境へ送出し、計算が停止する。

この例が示しているのは、単一の万能規則ではなく、次の組合せによって計算を組み立てられることである。

- 局所的な反応規則
- 段階ごとに異なる領域
- 優先度による制御
- 膜溶解によるフェーズ移行
- 最外層からの出力

結果として、このシステムは平方数の集合を生成する。

## 13. この章から得られる研究上の転換

第2章までの膜は、区画化、透過、通信、反応場として説明できた。第3章では、そこに次の要素が加わる。

- 領域ごとに規則が違う
- 同じオブジェクトでも所在によって可能な反応が違う
- 通信は宛先を伴う規則として記述される
- 境界の消滅が計算フェーズを変える
- 出力は最外層を越えて環境へ出たものとして定義される

したがって、SGOS膜理論を発展させる際には、膜を「情報を通すフィルター」とだけ捉えるのでは不十分である。

> 膜は、局所状態、局所規則、通信可能性、責務、寿命を一体として保持する実行単位である。

## 14. 暫定仮説

### 仮説1：Handoffはオブジェクト移動だけではない

Handoff時には、本文や成果物だけでなく、状態、責務、許可された次の規則が移る。P systemの `out` や `inj` よりも豊かな通信Envelopeが必要になる。

### 仮説2：Areaの終了は膜溶解として記述できる

専門Areaが終了するとき、その成果物と未解決事項は上位へ返され、Area固有の実行権限とルールは停止する。この過程をcloseout protocolとして形式化できる。

### 仮説3：Repository Contextは膜内環境である

Repository Contextは単一の入力オブジェクトではなく、ある領域でどの規則が適用可能かを決める局所環境として扱う方が近い。

### 仮説4：SGOSでは非同期膜モデルが必要である

P systemは全領域共通のglobal clockを仮定する。SGOSでは人間、ChatGPT、Codex、常駐Agent、GitHub Actionsが異なる時間で動く。したがって、同期macro-stepではなく、event-drivenかつ部分同期型の膜計算モデルが必要になる。

## 15. 誤読を避けるための注意

- 原著は組織論や生成AIシステムを論じていない。
- P systemのオブジェクトは意味を理解して反応する主体ではない。
- 膜ラベルは計算中に変化せず、主体の自己認識や役割変化を表さない。
- 原著の基本モデルは階層的な木構造であり、横断的ネットワークやリゾーム構造を直接表現しない。
- 最大並列性、同期実行、停止計算という仮定は、SGOSへそのまま移植できない。

## 16. 次章への問い

第4章では通信の組織化が扱われる。確認すべき問いは次の通りである。

1. `inj` の強い宛先指定は、SGOSのAgent identityやRoutingとどこまで対応するか。
2. 弱い宛先指定や電荷による通信は、役割・属性ベースRoutingとして読めるか。
3. 膜の透過性を動的に変える仕組みは、Selective Permeability、権限制御、緊急隔離とどう接続するか。
4. 隣接性チェックは、SGOS Communication Architectureの安全性に何を与えるか。
